# Compatibility Rules

This document outlines the bounds of structural compatibility in the PFP runtime. It governs how and when changes to configurations, mapping semantics, schemas, and runtime expectations are considered non-breaking, versus what constitutes a breaking change in data contracts.

This is a specific data contract definition, not a policy for software version governance or release processes.

## 1. Input Mapping Compatibility

The translation phase depends strictly on flat source key matching mapped to specific UM-space targets via `ConnectorFieldMapping`.

**Compatible Changes:**
*   Adding new source fields to input records without referencing them in mapping configs.
*   Declaring new mappings for existing source fields explicitly marked as `required=False`.

**Breaking Changes:**
*   Adding a `required=True` mapping targeting a field that does not consistently exist in the source input payload. In a `continue_on_error=False` setting, this forces mapping termination.
*   Changing a mapping target (`path`) that is required by the downstream target configuration.

## 2. Artifact Semantics Compatibility

The `ProducedArtifact.metadata` schema parameters dictate how downstream systems interpret the file format payload string/byte chunks.

**Compatible Changes:**
*   Adding new arbitrary fields to `ProducedArtifact.metadata.filename_hint` or introducing new text encodings (so long as standard ASCII/UTF-8 decoders remain unaffected by definition).
*   Introducing new non-interfering chunks to the payload end (for streaming additions if formatting supports appending).

**Breaking Changes:**
*   Changing the `schema_version` of an existing artifact shape. Applications statically parse `schema_version` and `target` (`SchemaRef` identity) to load processing policies.
*   Modifying structural expectations of generated bytes contrary to the expected output extension (e.g., placing JSON encoded lines within an artifact tagged structurally as CSV).

## 3. Diagnostics Interpretation

Validation diagnostics represent system evaluation flow.

**Compatible Changes:**
*   Adding new keys to the `metadata` JSON object within a `Diagnostic`.
*   Changing human-readable `message` fields within a `Diagnostic`.
*   Adding new `DiagnosticSeverity.INFO` or `WARN` diagnostics to the `ValidationReport`.

**Breaking Changes:**
*   Changing a previously returned machine-readable `code` used by users for assertion validation.
*   Upgrading an existing `WARN` diagnostic to an `ERROR` diagnostic (causes validation routines checking severity aggregates to fail ungracefully).
*   Alteration of the `ValidationReport` deterministic sorting outcome rules.
